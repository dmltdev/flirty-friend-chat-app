  we won't have to re-run the whole moderation logic - we'll just filter by the 
   message props.                                                               
  ⎿  Read src/app/api/chat/route.ts (86 lines)

⏺ Good catch. The root problem: when moderation blocks a user message the first
  time, we 400 without saving. The client still has that message locally and
  re-sends it in the next request's history — we then trust the client array,
  save it, and hand it to the LLM.

  Fix plan: tag messages with metadata.moderation.flagged, use server-stored
  history as source of truth (ignore prior client history), re-moderate only the
   new last message, then filter flagged messages out of the LLM context before
  streaming.

⏺ Not HMR (well, HMR exposes it). The bug is the dbCache Map in store.ts.

  What's happening:
  - dbCache lives at module scope. Next.js's dev server often ends up with
  separate module instances for the route handler graph vs. the page SSR graph
  (and HMR can refresh one graph but not the other).
  - The POST handler creates a Low instance, reads the file once, and stores it
  in its cache. replaceHistory mutates that cached db.data and writes to disk.
  Disk is now correct.
  - The page SSR graph has a different Low instance in its cache, with stale
  db.data loaded before the block was persisted. getHistory returns that stale
  in-memory array — we never .read() again after the first time.
  - Restart → every cache empties → next access re-reads from disk → blocked
  message reappears.

  So the cache is fine for a single process with a single module instance, but
  it breaks the moment any other execution path writes to the same file. Fix:
  drop the cache and .read() fresh each call (per-session files are tiny).

⏺ The bug is in the retry-after formula, not in the banner. Let me show the
  math.

  In rate-limit.ts:
  const retryAfterSec = Math.ceil(1 - bucket.tokens / REFILL_PER_SEC);

  With REFILL_PER_SEC = 2/60 ≈ 0.0333 and tokens = 0:
  - 0 / 0.0333 = 0
  - 1 - 0 = 1 → 1 second returned to the client.

  But actually refilling to 1 token takes 1 / 0.0333 ≈ 30 seconds. So the banner
   counts 1 → 0, shows "You can try again now", user clicks, server still has 0
  tokens, returns retryAfterSec: 1 again — infinite loop.

  Correct formula: (1 − tokens) / REFILL_PER_SEC.
